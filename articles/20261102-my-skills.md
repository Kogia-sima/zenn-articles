## Agent Skills一覧

### 1. `document-review`: 様々なドキュメントをレビューする汎用スキル

個人開発などで作成したドキュメント等をレビューすることが多いので、レビュー観点などをまとめたスキルを作成しています。

AIへの単純なレビュー依頼との大きな違いは下記2点です。

* AIに目一杯調べさせて、時間をかけてレビューさせている
* 出力フォーマットを統一することで、人間側の認知負荷を下げている

特に2つめの部分は大きいです。
Claudeが毎回レビュー結果を同じフォーマットで返してくるので、レビュー結果のどの部分を読めば良いかを判断する必要がありません。

生成AIの長い出力を読むのは負荷が大きかったので、これは正直やって良かったなと思ってます。

### 2. `idea-sparring`: ユーザの壁打ち相手となる汎用スキル

ユーザのやりたいことや課題などを整理して、解決策を提案します。
ミニコンサル的なイメージです。

このスキルのすごいところは、スキルを入れておくだけで、様々な場面におけるAIの批判的思考力が向上するところです。

例えば、ユーザがざっくりとした要望や雑なプロンプトを投げた際、いきなり解決策を提案するのではなく、まず「本当にやりたいこと」「現状」「真の課題」を推測・整理してユーザとすり合わせを行います。

前提をすり合わせてから提案に移るため、生成AIにありがちな「背景の前提や意図を汲み取ってくれない」という問題を回避することが可能です。

### 3. `python-testing`: Pythonのテストを実装・実行するスキル

アジャイルなどで開発を進めていると、開発スピードを担保するために、テストより先に実装を書かなければならない状況に度々出くわします。

既に実装がある状態でAIにテストを書かせてしまうと、「既存の実装が正しく動くかどうか」という観点でテストを書いてしまうため、要件に対する抜け漏れが発生しやすくなります。

このスキルは、そういった問題を打破するために作成されたスキルです。

具体的には、下記のフローに従ってテストを実装します。

1. リポジトリ内を探索し、要件定義書や仕様書を洗い出す
2. それらの内容から要件を整理する
3. 既存の実装ベースではなく、「要件を網羅的に検証する」という観点でテストを書く ← ★重要
4. テストを実行し、失敗した場合は失敗原因を分析し、問題個所と修正案をレポートにまとめ、ユーザに提示する

ただし、この方法でも100%要件漏れを防げるわけではありません。

テスト品質を向上させたい場合は、このスキルだけでなく、ミューテーションテストやプロパティベーステストなどの別手法も併せて用いることをおすすめします。

ちなみに現在は Python にのみ対応していますが、今後は他の言語にも対応させたいと思っています。

### 4. `adr-writer`: メモ書きからADR (Architecture Decision Records) を生成するスキル

大規模システムや長期間運用するようなシステムの場合、ADRの存在は非常に重要です。

誰かが設計書を書いたとしても、後から要件が変わった際などに、「本当にこの設計は必要なのか」を他の人が判断できないからです。

特に最近は技術の変化が速いため、要件や前提は刻一刻と変わっていきます。

このスキルは、雑なメモをADRに変換するスキルです。
メモに不足している情報があれば、AIがヒアリングを行ってくれるので、メモの品質を気にする必要はありません。

## スキル作成・管理のポイント

### 1. スキルは日本語で作成する

フリーランスや外資系企業等でない限り、スキルは日本語で作成した方が良いです。

そのほうが他の人も読みやすいですし、管理がしやすいです。

「英語で書いた方が精度が上がる」というのも事実ですが、年々日本語と英語の精度差は縮まっていますし、個人的には管理上のメリットの方が大きいと感じています。

### 2. 汎用的なスキルでも効果はある

「`document-review` スキルを使うのと、AIに直接レビュー依頼するのでは何が違うのか？」

という人がいるかもしれませんが、全然違います。

汎用的なスキルを作ることには、主に4つのメリットがあります。

①`/<スキル名>` ですぐに呼び出せるので、プロンプトを打つ手間が省ける
②AIの出力フォーマットが毎回同じなので、人間側の認知負荷が下がる
③どのような業務の頻度が高いかが一目でわかる（スキルの呼び出し回数を計測することで、業務頻度を計測できる）
④汎用的に使えるので、一度作れば使い回せることが多い

特に④の部分は大きいです。仕事で作ったスキルなら組織内にそのまま共有できますし、個人で作ったスキルなら、GitHubリポジトリに公開してたくさんの人に使ってもらうことが可能です。

逆に、業務特化のスキル（特定のデザインに沿った提案書作成など）は他の人が使いづらいため、せっかくスキルを作っても自分だけの効率化に留まってしまいます。

### 3. Skillsそのものよりも、仕組みや事例の方が速く浸透する

Skillsを社内やチームに共有したい場合に重要なのは、

**「単にSkillsの魅力を伝えるだけでは誰も使ってくれない」**

ということです。

私自身、社内チャットでスキルを何度か自慢げに宣伝したりしてきたのですが、
Claudeの管理コンソールで実際の利用者数を見ると、誰も使っていませんでした。

様々な方法を試したのですが、結果的に効果が表れたのは

* 「Agent Skillを使う仕組み」を取り入れる
* Skills本体ではなく「事例」を共有する

のいずれかのアクションを行った時だけでした。

前者の仕組みというのは、例えば手順書やリポジトリに直接Skillsを埋め込むということです。何かしらの業務の手順書を作成する際にSkillsの利用手順を埋め込むことで、必然的にSkillsを使わざるを得ない状況を生み出します。

後者に関しては、実際の仕事でスキルを使ってみた結果と、その際のアウトプットを共有することで、多くの人が反応してくれたという経緯があります。多くの人はSkillsそのものに興味がないので、「いかにして認知を興味に移行させるか」というところが課題となります。

## まとめ

本記事では、自作したAgent Skillsと、そこから得た学びをまとめました。

Agent Skillsは業務を効率化する便利な道具ですが、個別業務だけでなく、汎用的なスキルを作ることで、チームや組織全体の効率化につなげることも可能です。

今後は、単に自分のためにスキルを作るのではなく、**他の人も使ってもらう前提でスキルを汎用化し、尚且つそのスキルを容易に使うことができる仕組みを作る**ことが、AIの組織浸透を進めるうえで重要と考えられます。
